# 技術計画書

企画書（`docs/01-overview.md`）のうち、技術に関わるものをまとめる。
2章の技術スタックはチームで合意済み。

## 1 決まっていること
- LLM の出力は JSON で構造化する（問い・式・変数・単位・正解・解説・出典）。条件変更のスライダーは、この式と変数を使ってアプリ側で再計算する
- LLM に送る画像は囲んだ範囲の切り抜きだけにする（全体の画像は送らない）
- 応答待ちを短くするため、囲んだ直後に LLM の呼び出しを始め、認識結果の確認中も裏で問いを作る（先読み生成）
- 通信はオンライン必須（通信できないときはエラーを表示する）
- アーカイブはクラウド（Firestore）に保存する（写真は切り抜きのみ。画像も Firestore に入れ、Storage は使わない）
- 認証は自作せず Firebase Authentication を使う（パスワードリセットはなし。理由は2.1）
- API の利用回数はハッカソン期間中は制限しない
- MVP ではテストを書かない（フェーズ 3-0 で入れる）

## 2 技術スタック
| 項目 | 決定 | 理由 |
|---|---|---|
| プラットフォーム | Web アプリ（PWA） | URL を開くだけでスマホ実機で動き、ストアへの提出が要らない |
| フロントエンド | Next.js（React + TypeScript） | 画面とサーバー側の処理（LLM の呼び出し）を1つのリポジトリで書ける |
| CSS | Tailwind CSS | スマホ幅への対応が書きやすく、分担しても書き方がそろいやすい。色・影・角丸は `docs/design/tailwind-theme.css` と同じ値を `src/app/globals.css` の `@theme` に置く。フォント（Mochiy Pop One・Zen Maru Gothic）は `next/font/google` で読み込む |
| パッケージ管理 | npm | 全員が追加のインストールなしで使える |
| DB | Firebase（Firestore） | 導入が速く、セキュリティルールで「本人だけ」を制御できる |
| 画像の保存先 | Firebase（Firestore に直接保存） | Storage は従量課金の Blaze プラン（クレジットカード登録）が必須のため。切り抜き画像は数百KBで、1件 1MiB の上限に収まる |
| 認証 | Firebase Authentication | 認証を自作しない。Firestore のルールと連携できる |
| ホスティング | Vercel | Next.js をそのまま公開できる。HTTPS なので、スマホでカメラを試せる（公開のしかたは 10章） |
| LLM | Claude（既定は Opus 5.5 `claude-opus-5-5`。本番は Sonnet 5.5 `claude-sonnet-5-5`・effort low） | 画像入力と JSON の構造化出力に対応。本番は、待ち時間と費用のバランスで Sonnet にしている（9章の実測） |
| 式の計算 | math.js | LLM が出した式を、eval を使わずに安全に計算できる。単位の変換もできる |
| JSON の検証 | Zod | JSON の形を1か所で定義し、型と検証の両方に使える |

- 使うパッケージ（予定）：`next` `react` `tailwindcss` `firebase` `@anthropic-ai/sdk` `mathjs` `zod`。追加するときは AGENTS.md の禁止事項3に従って確認する

### 2.1 認証の方式
- ログイン ID はユーザー名。内部で `<ユーザー名>@<FirebaseのプロジェクトID>.firebaseapp.com` に変換して、Firebase Authentication のメール／パスワード方式で登録する（アプリからメールは送らない）
- ユーザー名にはひらがなも使えるようにする。メールアドレスに使えない文字があるため、ユーザー名を英数字に変換（例：UTF-8 のバイト列を16進数にする）してからメール形式にする
- 変換するとひらがな1文字が6文字になる。メールアドレスの `@` より前は64文字までなので、ユーザー名の長さの上限：【未決】（16進数なら10文字程度）
- メールアドレスを集めないため、パスワードリセットはできない（パスワードを忘れるとアーカイブに戻れない）
- 1つのアカウントの中に複数のプロフィール（子どもごと）を持つ
- 学校版（未実装）：Google・Microsoft のログインと、学校のメールアドレスとパスワードの方式を足す。いまの方式も残す（`docs/06-school-expansion.md` 3章・10.1）

### 2.2 LLM の呼び出し
- Next.js の Route Handler（サーバー側）から公式 SDK（`@anthropic-ai/sdk`）で呼ぶ。`ANTHROPIC_API_KEY` はサーバー側の環境変数だけに置く
- API はログインした人だけが呼べるようにする。画面から Firebase の ID トークンを送り、サーバー側で、Google の公開鍵を使って署名・期限・発行元・対象を検証する（`src/server/auth.ts`。`firebase-admin` は本番の Vercel で読み込みエラーになったため使わない）（URL を知っている人に使われて課金が膨らむのを防ぐ）
- 出力は構造化出力（`output_config.format`）で JSON の形を指定し、受け取った後に Zod でも検証する
- 断られたとき（`stop_reason: "refusal"`）は別のモデルに切り替えず（`fallbacks` は使わない）、「別のものを囲んでみてね」と表示する。`content` を読む前に必ず `stop_reason` を確認する
- effort（考える深さ）の既定は medium。環境変数 `LLM_EFFORT` で変える（本番は low）。待ち時間はナビゲーターキャラの豆知識（まめちしき）でつなぐ
- 料金と時間の目安：9章の実測（モデルと設定で、1回あたり約 0.3セント〜12セント、3秒〜45秒）

### 2.3 Vercel の制限（Hobby プラン）
- 関数の実行時間：最大 300 秒。60 秒で打ち切る（5.4）ので収まる。ストリーミングは使わない
- リクエスト・レスポンスの大きさ：4.5 MB まで。画像を長辺 1024px に縮小する（5.1）ので収まる
- 関数が動く地域：初期設定はアメリカ（`iad1`）なので、東京（`hnd1`）にしている（`vercel.json`）
- Node.js：22.12 以上（`package.json` の `engines`）。Vercel のプロジェクト設定は 24.x

## 3 全体構成
```
[スマホのブラウザ（Next.js の画面）]
   │  撮影・囲む・切り抜き・縮小・予想・可視化・math.js で再計算
   │
   ├─ Firebase Authentication ……… ログイン（ID トークンを受け取る）
   ├─ Firestore ………………………… プロフィール・アーカイブ・切り抜き画像を読み書き（ルールで本人だけ。グループの投稿はメンバーだけ）
   │
   └─ Next.js の Route Handler（Vercel・東京）
         │  ID トークンを検証（Google の公開鍵）
         └─ Claude API（API キーはここだけ）
```
- クライアント：撮影、囲む操作と切り抜き、予想の入力、可視化、再計算、アーカイブの表示。Firebase に直接読み書きする
- サーバー：LLM の呼び出しだけ。DB には書かない（保存は画面から行う）
- 学校版（未実装）では、招待コードの確認・自動チェック・通報のために、サーバーの役割を見直す可能性がある（`docs/06-school-expansion.md` 10.3）

## 4 処理の流れ
```
撮影 → 囲む → 切り抜き・縮小（EXIF も消える）
  → /api/questions に「画像 + 学年 + 出題済みの組み合わせ」を送る（ここから裏で生成）
  → 「これは○○だね？」の確認（違えば修正して作り直す）
  → 問い 3 つ（JSON。予想とこたえあわせに必要な分だけ）→ 検証・math.js で正解を計算 → 選ぶ（ここで /api/questions/detail を呼び、その1問の解説などを作る）→ 予想
  → 答え合わせ・可視化 → スライダーで再計算 → アーカイブ保存（Firestore）
```
- 自分で問いを書いた場合は、`/api/questions/custom` に「画像 + 学年 + 問いの文」を送り、同じ形の問いを 1 つ受け取る（解説なども1回で全部そろう）
- 出力は2回に分ける（#165。5.4）：1回目 `/api/questions` は問い3つ（予想とこたえあわせに必要な分だけ）、2回目 `/api/questions/detail` は子どもが選んだ1問の解説など（画像なし）
- 認識結果を修正したときは、修正した名前を付けてもう一度呼ぶ（ユーザーの操作で呼ぶ1回であり、自動リトライではない）

## 5 LLM
### 5.1 入力
- 画像：囲んだ範囲の切り抜きだけ。ブラウザの Canvas で長辺 1024px の JPEG に描き直す（このとき EXIF も消える）。保存用（Firestore）にも同じ画像を使う
- 学年（大まかな目安）
- 学習の進み具合（問いを深くするため。測り方は `docs/02-spec.md` 17章：経験の点数で決めたレベルを、さいきんの手ごたえで1つ上げ下げする）。全体のレベル `level` と、教科ごとのレベル `subjectLevels: { math, science, info }`（前の版のアプリは送らないので、なくてもよい）
- 出題済みの「対象×分野（単元）」の組み合わせ（そのプロフィールのアーカイブから取り出す）
- 子どもの「どうだった？」（`docs/02-spec.md` 14章・17章。#164）：さいきん「おもしろい！」だった単元 `liked`（単元の名前だけ。新しい順に5つまで）と、さいきん10問のうち「むずかしい」の数 `hardCount`。どちらも前の版のアプリは送らないので、なくてもよい。プロンプトは `profileText` に1行ずつだけ足す。写真・問いの文・予想は送らない
- （修正時）ユーザーが直した認識結果／（自分で書く方式）問いの文

### 5.2 出力（JSON）
| 項目 | 内容 | 型・形式 |
|---|---|---|
| 認識結果 | 「これは○○だね？」に使う名前と、問いが作れるか | `recognition: { label: string, canAsk: boolean }` |
| 問い | 問題文（学年に合わせた漢字・ふりがな） | `questions[].text: string`（ふりがなは `{漢字\|よみ}` の短い記法で書かせる。熟語はことば全体に1つ付ける（`{前提\|ぜんてい}` ○／`{前\|まえ}{提\|てい}` ✕）。文はわかち書き。表示前に、22px 以上は `<ruby>` に、それより小さいときは読みに置きかえる（`src/lib/ruby.ts`）。それ以外のタグはすべて文字として表示する。古い `<ruby>` タグの保存データも読める） |
| 問いのタイプ | 数量推定・比較・「なぜ？」型 | `questions[].type: "estimate" \| "compare" \| "why"` |
| 分類 | 算数・理科・情報／単元／対象 | `subject: "math" \| "science" \| "info"`、`topic: string`、`target: string` |
| 式 | math.js で計算できる式。「なぜ？」型は null | `formula: string \| null`（例：`"length * width / tileArea"`） |
| 変数 | 名前・表示名・値・単位・スライダーの範囲 | `variables: { name, label, value, unit, min, max, step }[]` |
| 単位 | 答えの単位（学年で習ったもの） | `answerUnit: string` |
| 正解 | LLM が考えた値（確認用。表示には使わない） | `llmAnswer: number \| null` |
| 選択肢 | 「なぜ？」型の選択肢（理由・結果・どっち。2〜3つ。正解の印つき。AI は正解を1番目に書くので、`validate.ts` が返す前に1回だけ ランダムに並べかえる。保存される順が、そのまま画面の順。見本の問いも同じ。デモ版（`demo.ts`）は手で並べた） | `choices: { text, correct }[] \| null` |
| ねらい・入れかえ判定 | 内部で使うだけ（表示・保存しない）。ねらった「そのもののふしぎ」と、ものの名前を入れかえても成り立つか。問い生成では `swappable` を書かせない（下の「出力の形の大きさ」）。自分で書いた問いでは書かせる | `secret: string`、`swappable: boolean` |
| 問いのたね | 問い生成だけ。問いを書く前に5つ出させる（表示・保存しない）。「聞きかた｜子どもが ふつう 思っていること → 本当のこと｜おどろき1〜3｜たしかさ1〜3」の文 | `candidates: string[]`（`questions` より前） |
| 直感の数 | 問い生成の数で答える問いだけ。その学年の子どもが 計算せずに 言いそうな数（検査に使い、保存しない。「なぜ？」型は 0） | `questions[].naiveGuess: number` |
| たしかさ・わけ | 正解の事実の たしかさ（AI の自己申告）と、大人が たしかめられる1文（#161）。`certainty` が `guess` の問いは出さない。「なぜ？」型の正解の選択肢（や解説の一言）に「かもしれない」「と おもう」「らしい」「たぶん」が入る問いも出さない（`validate.ts`）。どちらも保存し、`basis` は なぞときの「おとなの 人へ」に出す（`certainty` は 画面に出さない）。前の記録には ない（型では optional）。自分で書いた問いは、`certainty` を書かせず（出力の形が大きすぎて断られるため。下）、たしかさで はじかない（`basis` だけ書かせる）。見本の問い・デモは `textbook` | `certainty: "textbook" \| "common" \| "guess"`、`basis: string`（`choices` の次） |
| 解説（2回目） | まず一言と、タップで見る計算過程のステップ | `explanation: { short: string, steps: string[] }` |
| 出典（2回目） | 根拠データ・前提条件 | `sources: { title: string, url: string \| null, assumption: string }[]` |
| ヒント | 問いの見かた・前提（答えのヒントではない） | `hint: string` |
| 身近なおきかえ | 答えを身近なものにおきかえる（`per`：答え÷value を「unit ぶん」、`times`：答え×value） | `ref: { type: "per" \| "times", label, value, unit } \| null` |
| 条件のといかけ（2回目） | 条件を変えたくなる一言 | `whatIf: string` |
| やってみよう（2回目） | 本物の ものに ふれて たしかめる、ごく安全な観察（`docs/02-spec.md` 12章。あぶない ことばがあれば、検査で空にする） | `tryIt: string` |
| 関連・しらべことば（2回目） | 同じ考えかたの別の問い（0〜2）・もっと調べるときのことば | `related: string[]`、`keyword: string` |

- 1回に出す問いの数：問い生成は 3 つ（3択方式のため）、自分で書いた問いは 1 つ
- 出力の分けかた（#165）：上の表のうち「（2回目）」をつけた項目（`explanation`・`whatIf`・`tryIt`・`related`・`keyword`・`sources`）は、問い生成の1回目には書かせない（`schema.ts` の `DraftQuestionSchema`。2回目は `DetailSchema`）。`ref`（身近なおきかえ）は こたえあわせの画面で出すので 1回目に残す。自分で書いた問い（`CustomOutputSchema`）と見本の問いは、いままでどおり1回で全部そろう
- 出力の形の大きさ：形（Zod）が大きすぎると、API が「compiled grammar is too large」（400）で断り、問いが1つも作れない。2026-11-13 の時点で上限ぎりぎりなので、項目を足すときは、ほかを減らしてから、本物の API で1回確かめる。わかっていること：null もありの項目（`.nullable()`）や、説明（describe）をつけた配列は大きくなる。自分で書いた問いの `reason` は、null もありにすると断られていた（#124 で `tryIt` を足してから）ので、文字（答えられるときは空）にした
- 比較型の式と答えの持ち方（いまの実装。決めきれていない点は【未決】）：
  - 持ち方：`compare: { a, b }` に比べる2つの名前（ふりがな記法つき）、`formula` に「a ÷ b」の式（変数は2つ以上でもよい。`variables` で条件を変えられる）、`answerUnit` は「倍」。`llmAnswer` は式の答えと5%以内でなければ出さない
  - 答え：`formula` の値（a ÷ b）。1以上なら a が大きい、1より小さければ b が大きい。画面に出す答えは「大きいほうが小さいほうの何倍か」（`max(値, 1/値)`）。数直線・もしものグラフも同じ値で出す
  - 予想：どちらが大きいか（`side`）と、何倍か（`ratio`。1以上）。`side` を間違えたら「大はずれ」。合っているときだけ、`ratio` を答えの倍率と比べて ピタリ・おしい・大はずれ を決める（`src/lib/rating.ts`）
  - 見本の問い：信号の「青の時間は、黄いろの時間の何倍？」（`green / yellow`＝40÷3＝約13.3倍）。見本の問いにも、1年生には出さない決まりをきかせる（`src/server/llm/generate.ts`）
  - 【未決】a と b の どちらを「大きくなりそうな ほう」にするかは AI まかせ（答えが1より小さい問いも出る）。式に2つ以上の量（a・b が別々の変数）を使うか、1つの式の中で比べるかは、決めていない
  - 【未決】2択をはずしたとき、倍率が近くても「大はずれ」になる（見本の信号で、青ではなく黄いろを選ぶと「大はずれ」で、数直線には倍率の予想が出る）。倍率だけでも評価するかは、決めていない
- 「なぜ？」型の正解の担保の仕方（#161）：式で検算できないので、AI に たしかさを申告させる。プロンプトで「写真の中の絵・文字・マークの意味を すいそくで 正解にしない」「正解は どの○○にも あてはまる しくみ・きまりにする」と指示し、`certainty` が `guess` の問いと、正解があやふやな ことばの問いを、コードではじく。AI の自己申告なので、完全ではない。2026-11-14 に、`certainty` と `basis` を足した形が API に受けつけられることを、3つのモデルで確かめた（自分で書いた問い（`CustomOutputSchema`）は、両方を足すと断られたので、`basis` だけ）
- 正解の担保の仕方：
  - 表示する正解は、math.js で式と変数から計算した値を使う（LLM の値は使わない）
  - LLM の値（`llmAnswer`）と計算値が大きくずれる問いは、式が間違っているとみなして出さない（ずれの許容範囲：5%以内）
  - 3 つとも出せないときはエラー表示にする

### 5.3 プロンプト
- いちばん大事なのは、囲んだ「そのもの自身」への「なんで？」（正解を当てさせるテストにしない）。問いは、そのもののふしぎ・しくみ・ひみつにする
  - よい問いの条件を、優先の順に5つにしぼって書く：①そのもの自身のふしぎ ②思いこみが ひっくり返る ③直感で予想できる ④事実がたしか ⑤みじかい（#160）
  - 3つの問いは、聞きかた（なぜ？・どうなる？・どっち？・どれくらい？）を ばらばらにし、「なぜ／どうして／なんのため」で始まる問いは1つまで。3つの「本当のこと」は、それぞれ ちがう話にする（同じ ふしぎを 聞きかたを かえて 2回 聞かない）
  - 問いを書く前に、問いのたね（`candidates`）を5つ出させ、たしかさ 3（図鑑・教科書に のっている）のものだけから、おどろきが高く、聞きかたが ばらばらになる3つを選ばせる（先に広く考えさせて、毎回 にた問いに かたよらないようにする）
  - 問題文は、みじかい1〜2文。細かい条件や専門の数・ことば（「1びょうに44100かい」など）をならべない
  - そのものと関係のないもの（ゾウ・ビル・月 など）との大きさくらべにこじつけた問い、ものの名前を入れかえても成り立つ問いは作らせない
  - 3つのうち「なぜ？」型を1つ以上、数で答える問いは あわせて2つまで。数で答える問いは、そのもの自身に自然な数があるときだけ1つ入れる（むりに作った「使う時間 × 日数」や、ありえない場合の数にした問いは作らせない。#101）。写真を見て数えられる数は、答えにせず条件に使う。subject（算数・理科・情報）はなるべくばらばらにする
  - 算数（math）の問いは、どのものにも言える かけ算（「1日2時間つかうと1年で何日」など）にしない。そのものがかくしている、かたち・ならび・くりかえし・つくりの数（ならべかたの数、部分と全体の大きさ、ふえかた、確率・平均）を選ばせる
  - 数で答える問いは「計算の問題」ではなく「直感が はずれる問い」にする。問題文に計算に使う数を書かせない（数は variables と sources に置く）。直感が はずれやすい型（ふえかた・場合の数・確率と平均・比としくみ・形のきまり・つみかさね）を、そのものに自然に合うときだけ使わせる。「数えるだけ」「1回のかけ算で出る」「答えが問題文に書いてある」問いは作らせない
  - 算数は、数で答えなくてもよい。形・ならび・きまりの「なぜ？」「どうなる？」（ハチの巣は なぜ 六角形？ など）も算数の問いにする
  - 仕組み：出力の形に、ねらい（`secret`）を問題文より先に書かせる。次の問いは出さない（`src/server/llm/validate.ts`。自分で書いた問いと見本の問いは対象外）。`secret`・`swappable`・`candidates`・`naiveGuess` は保存しない
    - `swappable` が true の問い（自分で書いた問いだけで書かせる）
    - 問題文が140字をこえる問い。数が3つ以上（1をのぞく）または10000以上の数が入った問い
    - 数で答える問いで、問題文に数が2つ以上ある、または問題文とヒントを合わせて3つ以上ある問い（数がならんだ文章題）
    - 数で答える問いで、直感の数（`naiveGuess`）と答えが1.5倍より近い問い（予想がはずれない。2倍にすると、ガチャを ぜんぶ そろえる平均のような よい問いまで落ちた）
    - 数で答える問いで、式で使われない変数は外す（もしもの スライダーが きかないため）。1つも使わない式（円の まわりは はばの 何倍？＝`pi` など）は、スライダーなしで出す（もしもの画面は出ない）
- 直感が外れやすい問いの例を与える
- 確率・場合の数の式用に、`harmonic(n)`・`fact(n)`・`comb(n,k)`・`birthday(n)` を使えるようにしてある（`src/lib/calc.ts`）
- 学年に合わせた問い・漢字・単位にする
- むずかしいことば（前提・仮定・根拠 など）を使わず、やさしいことばに言いかえさせる（言いかえの表は `docs/02-spec.md` 2.2）。出力の形の説明（`schema.ts` の describe）にも、むずかしいことばを書かない（AI がそのまま使うため）
- 出題済みの組み合わせと同じ問いを出さない
- 子ども向けとして不適切・危険な内容（火・刃物・電気・薬品・高い所・道路など）を出さないよう制約する
- 計算は LLM にさせず、式と変数を出させる
- 置き場所：LLM まわりは `src/server/llm/` にまとめ、画面側から import できないようにする（`server-only`）
```
src/
  app/api/questions/route.ts         … 問い生成
  app/api/questions/custom/route.ts  … 自分で書いた問い
  app/api/questions/detail/route.ts  … 選んだ1問の解説など（2回目）
  server/llm/prompts.ts              … プロンプト（ここだけに書く）
  server/llm/schema.ts               … JSON の形（Zod。検証と型に使う）
  server/llm/client.ts               … Claude の呼び出し
```
- アプリ全体のディレクトリ構成は AGENTS.md を参照
- プロンプトのキャッシュ（#165）：`client.ts` の `callStructured` は、system を `cache_control: { type: "ephemeral" }` つきで送る。システムプロンプトは約14,000トークンあり、毎回同じなので、2回目からは入力のほとんどがキャッシュから読まれ、入力の費用が下がる（読み出しは、通常の入力の 0.05 倍：Sonnet 5.5 で 100万トークンあたり $0.10。最初の書き込みは 1.25 倍）。キャッシュは5分で切れ、別の人の呼び出しにも効く（system が同じなので）
  - **system に、学年・進み具合・出題済み・日付・乱数を入れない**（1文字でも変わるとキャッシュが使えない）。それらは `questionsUserText`・`customUserText`（user 側）に置く。`SYSTEM_PROMPT` の中の学年ごとの単元の表は、固定の定数なので問題ない。プロンプトを書きかえると、最初の1回だけキャッシュの書き込みになる
  - キャッシュできる最小の長さは、Sonnet 5.5・Opus 5.5 で 512 トークン（システムプロンプトは余裕で超える）。画像・user のテキスト・出力の形（`output_config`）は、キャッシュの前の部分ではないので、毎回変わってよい
  - 確かめかた：サーバーのログ `[llm]` の `cacheRead`（キャッシュから読んだトークン）と `cacheWrite`（キャッシュに書いたトークン）。2回目の呼び出しで `cacheRead` が 0 より大きければ効いている。2026-11-13 の実測（Sonnet 5.5・effort low・同じ写真・同じ学年）：1回目 `cacheWrite` 14,267・`cacheRead` 0・22.8秒、2回目 `cacheRead` 14,267・`cacheWrite` 0・19.2秒（`inputTokens` はどちらも 1,903）
  - 待ち時間はほとんど縮まない（時間の大半は出力を書く時間）。キャッシュで下がるのは主に費用。待ち時間は、出力を2回に分けて縮めた（5.4）
  - 1回目と2回目は、出力の形（`output_config`）が ちがうので、system が同じ文字でも、キャッシュは別々に作られる（2回目の呼び出しの最初の1回は `cacheWrite`）。同じ形の呼び出しどうしは、5分以内なら `cacheRead` になる（2026-11-13 の実測：1回目の形を続けて2回呼ぶと、2回目が `cacheRead` 13,075）

### 5.3.1 出力を2回に分ける（#165）
- 理由：1回で全部書かせると、約18〜20秒・出力 約2,000トークンかかり、その大半は、子どもが選ばなかった2問の解説・出典・やってみよう・関連の問い（すてられる）だった。時間の大半は出力を書く時間なので、出力を分けて、はじめの待ちを減らす
- 1回目（`/api/questions`。画像つき）：認識（`recognition`）・問いのたね（`candidates`）・問い3つ。問いには、予想とこたえあわせに必要な分（`text`・`type`・`subject`・`topic`・`target`・`hint`・`formula`・`variables`・`answerUnit`・`llmAnswer`・`guessRange`・`compare`・`choices`・`ref`・`naiveGuess`）だけを書かせる。**式の計算と検算（`validate.ts`）は1回目で終える**（答えを先に見せない・計算はコード）。返す問いの解説などは空（`explanation.short` が空）で、`src/lib/questionDetail.ts` の `needsDetail` で「2回目が要る」と分かる
- 2回目（`/api/questions/detail`。画像なし）：問いの文・型・単元・対象・ヒント・式・変数・単位・比べる2つ・選択肢と正解・学年・進み具合だけを送る（`request.ts` の `DetailRequestSchema`。長さと個数を制限）。サーバーが式から答えを**コードで計算**して AI に渡し（`prompts.ts` の `detailUserText`）、AI には そのわけを書かせる（問いの文・正解・答えは変えさせない）。受けとった解説などは、1回目と同じ決まり（あぶないことばの検査・URL の検査・関連の数）で確かめる（`validateDetail`）。式が計算できない・正解が決まらない問いは、AI を呼ばずに 502 にする
  - プロンプト：`SYSTEM_PROMPT` は1回目と2回目で共通（「# 出力」の章に、2回に分かれることを書いてある）。2回目だけの指示は user の文（`detailUserText`）に置く
  - 出力の形：`DetailSchema`（`QuestionSchema` から、解説・もしもの問いかけ・やってみよう・関連・しらべことば・出典を取り出したもの）。1回目の形（`QuestionsOutputSchema`）も、2回目の形も、本物の API で受けつけられることを確かめた（画像なし・`max_tokens: 20`。Sonnet 5.5・Opus 5.5）
- 画面：問いを選んだとき（`QuizProvider` の `selectQuestion`）に、2回目を呼ぶ。結果は問いごとに覚える（もどって同じ問いを選んでも呼びなおさない）。`useQuiz()` の `detail`（`none`・`loading`・`ready`・`error`）と `retryDetail` を、`/result` の「なぞとき」が使う（`docs/02-spec.md` 12章）。保存（`SavePanel`）は、解説が届くまでしない
- 見本の問い（`builtin.ts`）・デモ（`demo.ts`）・`LLM_MODE=mock`・自分で書いた問い（`/api/questions/custom`）は、1回で全部そろい、2回目を呼ばない
- 使いすぎの歯止め：2回目も AI を呼ぶので数える。1回目（と `custom`）とは別の入れものに数える：1分12回・1日200回（`RATE_LIMIT_DETAIL_MINUTE`・`RATE_LIMIT_DETAIL_DAY`）。1回目は これまでどおり 1分6回・1日100回。1枚の写真で、1回目 1 ＋ 2回目 1〜3回（3つを見くらべたとき。同じ問いは覚えているので呼びなおさない）。同じ入れものにすると、3つを見くらべただけで 1分6回に近づくため分けた（2回目は 画像がなく 出力も少ないので、費用は 1回目の 3分の1ほど）
- 実測（2026-11-13・Sonnet 5.5・effort low・マンホールの写真・5年生・本物の API）：

| 呼び出し | 時間 | 入力 | 出力 |
|---|---|---|---|
| いままで（1回で全部） | 18〜20秒 | 約17,000 | 約1,900〜2,100 |
| 1回目（問い3つだけ） | 14.6秒・14.0秒 | 1,922 | 1,283・1,460 |
| 2回目（選んだ1問の解説など） | 8.8秒 | 497（system は `cacheWrite` 10,088） | 816 |

  - はじめの待ちは 約20秒 → 約14〜15秒（約25〜30%減）。目標の10秒以下には届いていない（残りの出力の大半は、問いのたね `candidates`・3問ぶんの `secret`・選択肢）。2回目の約9秒は、子どもが予想を入れている あいだに終わる（予想がすごく早いと、「なぞとき」で短く待つ）
  - 合計の出力は 約2,100（1回目 1,300〜1,500 ＋ 2回目 約800）で、1問ぶんだけ書くので、全部書いていたときと同じくらい。1回で3問ぶん書いていた解説のうち、2問ぶんを書かなくなった（費用は、選んだ問いが1つなら 少し下がる）
  - 【未決】1回目を さらに短くするなら、`candidates`（問いのたね）を減らす・やめる案がある（問いの質に かかわるので、#160 の作りかたと あわせて決める）

### 5.3.2 問いの評価スクリプト（#159）
- 目的：プロンプトを直したとき、同じ写真・同じ学年で、直す前と後を くらべる（「よくなった気がする」で決めない。直したせいで別の所が悪くなるのに気づくため）。#101 の ほかの Issue は、これで確かめる
- 使いかた（Node 24 でそのまま動く。新しいパッケージは足していない）：

```
npm run eval:questions                          # eval/images/ の全部の写真 × 学年 1・3・6
npm run eval:questions -- --only sushi.jpg      # 1枚だけ（--only sushi でもよい）
npm run eval:questions -- --grades 3            # 学年をしぼる（例: 1,3,6）
npm run eval:questions -- --level 2             # 学習の進み具合（既定は 1）
npm run eval:questions -- --dry-run             # AI を呼ばずに、回数と写真だけ見る
```

- 中身：`scripts/eval-questions.mts`。本物と同じ道（`SYSTEM_PROMPT`・`questionsUserText`・`QuestionsOutputSchema`・`callStructured`・`validateQuestion`、1年生の compare はずし）を通す。`server-only` と `@/` を Node で読めるよう、`--conditions=react-server` と `scripts/alias-loader.mjs`（`@/` と拡張子なしの import を src の `.ts` に読みかえる）を使う。`.env.local` の `ANTHROPIC_API_KEY`・`LLM_MODEL`・`LLM_EFFORT` を読む（`LLM_MODE=mock` のときは止まる）
- 評価するのは 1回目（問い3つ）だけ。解説・やってみよう・出典は 2回目（5.3.1）で書かせるので、報告には出ない
- 写真：`eval/images/*.jpg`（長辺 1024px 以下・人が写っていないもの。EXIF が残っていると止まる。写真は人間が用意する。コミットする）
- 出力：`eval/out/<日時>.md`（git 管理しない）。先に集計の表、そのあと 1問ごとに、写真・学年・type・subject・問題文・選択肢（正解に ✔）・式と答え・たしかさ・検査で落ちた理由・かかった時間・トークン数。集計は、検査で落ちた割合・type の内わけ・数で答える問いが1つもない写真×学年の割合・3問とも同じ subject の割合・問題文の長さと数の個数・「なぜ／なんのため／どうして」で始まる割合・学年で習っていない漢字の数（`src/lib/kanji.ts` の `isLearned`）
- 費用のめやす：1回 約3セント × 枚数 × 学年（9枚 × 3学年 ＝ 27回で 約0.8ドル）。1回の実行は **40回まで**（こえると呼ばずにエラー）。失敗した回は、自動で やりなおさず、失敗として報告に残す。テスト・CI・ビルドからは呼ばれない（手で動かすときだけ）
- 使いかた（くらべるとき）：プロンプトを直す前に 1回、直した後に 1回 動かし、2つの報告の「集計」を くらべる。モデル・effort・学年を そろえる。AI の出力は毎回ちがうので、1つの数の差だけで決めず、1問ごとの結果も読む
- 報告に、API キーと 画像の base64 は出ない（画像は `../images/<ファイル名>` で参照するだけ）

### 5.4 エラー処理
- 形式の崩れ・タイムアウト・API エラー・断られたとき・ID トークンが無効なときに、子どもにも分かるメッセージとやり直すボタンを出す
- タイムアウト：60 秒（囲んでから問いが出るまでの目標も60秒以内。待ち時間はナビゲーターキャラの豆知識でつなぐ）
- 断られたとき（refusal）：別のモデルには切り替えず、「別のものを囲んでみてね」と表示する
- 自動リトライはしない（課金とレート制限のため。SDK の自動リトライも 0 にする）
- 2回目（解説づくり）が失敗したとき：「なぞとき」に ナビの文と「もう一度 ためす」（2回目だけを呼びなおす。ユーザーの操作で呼ぶ1回）と「ほかの はてなを えらぶ」を出す。解説が届くまで、ずかんには保存しない
- 見本の絵（ガチャ・信号・氷のコップ）を使っているときだけ、AI が使えなければ、AI を呼ばずに見本の問い（`src/server/llm/builtin.ts`）に切り替える（ユーザーの操作ではなく、エラー時に1回だけ。画面に「みほんの もんだい」と表示する）
- ログに画像・トークン・API キーを出さない

- 画像の大きさ：Firestore の1件は 1MiB まで。base64 にすると元の約1.33倍になるので、JPEG の品質を調整して 1件が 1MiB 未満に収まるようにする
- ずかんの読み込み（#88）：ずかんは、ログインのたびに全件を読む。前は1件に大きな切り抜き（最大 約600KB）が入っていて、100件で最大 約60MB になった。いまは1件 約5KB（小さな画像 約4KB をふくむ）。前の記録は大きいまま（移すには人間の許可が要る。まだ移していない）。スタンプ・称号・出題済みの組み合わせは、画像を使わずに数える
- アクセス制御：Firestore のセキュリティルール（`firestore.rules`）で、`users/{uid}` の下は uid が自分のときだけ読み書きできるようにする。グループの分は下の「グループ」のとおり。ルールに書いていないもの（やめた `public`・`publicOwners` など）は、だれも読み書きできない。アーカイブの項目はルールでしばっていないので、`feeling` を足してもルールは変えない（グループの投稿 `posts` は項目をしばっているが、`feeling` は入れない）
- 全員への匿名公開（`public`・`publicOwners`・「みんなにも みせる」）は、グループの共有（#120）に置きかえて、やめた（2026-11-06 に決めた）。コードとルールから消した。前の投稿は #82 で消してある。古いアーカイブに `publicId` が残っていることがあるが、使わない

  - グループの文書（`groups/{groupId}`）・管理者・C専会のメンバーは、人が Firebase のコンソールで作る（アプリからは作れない。作る・変えるのは人間の許可を取ってから）

## 9 費用と待ち時間（実測）
2026-10-24 に、タイルの床のテスト画像（切り抜き・学年4年生・問い3つ）で、本物の API を1回ずつ測った値。1回の測定なので、ばらつきがある。入力は約6,700トークン（画像とプロンプト）。

| モデル・設定 | 時間 | 出力トークン | 1回あたりの費用 | 問いの質 |
|---|---|---|---|---|
| Haiku 5.5・effort=medium | 28秒 | 4,849 | 約 $0.003 | 答えのヒントが多く、驚きが少ない |
| Haiku 5.5・medium・考える処理オフ（`LLM_THINKING=off`） | 9〜10秒 | 1,166 | 約 $0.001 | ヒントが問題文に入り、驚きがない |
| Sonnet 5.5・effort=low | 13秒 | 1,465 | 約 $0.03 | 写真のタイルを数えた問いが出る。標準的 |
| Sonnet 5.5・effort=medium | 16秒 | 2,409 | 約 $0.04 | 同上 |
| Opus 5.5・effort=medium | 45秒 | 4,691 | 約 $0.12 | 驚きのある問い（点の数の比較など）。いちばん良い |

- 出力トークンには、考える処理の分も含まれる（Opus・Haiku の既定では、これが時間と費用の大半を占める）
- 計算の元の料金は、100万トークンあたり：Haiku 5.5＝$0.10／$0.50、Sonnet 5.5＝$2／$10、Opus 5.5＝$4／$20（入力／出力）
- 1回あたりの時間と費用を測るには、サーバーのログ `[llm]` の `ms`・`inputTokens`・`outputTokens` を見る
- 待ち時間は、いまは認識結果の確認の前に、問いがすべてそろうまで待つ。短くするには、認識結果だけを先に速いモデルで返し、問いは裏で作り続ける案がある（未実装）
- モデルは環境変数 `LLM_MODEL`（`claude-opus-5-5`・`claude-sonnet-5-5`・`claude-haiku-5-5`）、考える深さは `LLM_EFFORT`、考える処理のオフは `LLM_THINKING=off`（Haiku だけ）で変える
- 利用が多いときは API が 429（混雑）を返す。画面には「すこし まってから もういちど ためしてね」と出す（自動で再試行はしない）
- 使いすぎの歯止め（#166）：登録はだれでもできるので、アカウントを作って API を呼びつづけられると費用を使わされる（1回 約3セント）。`src/server/llm/handler.ts` が、ログインの確認のあと、利用者（uid）ごとの回数を数える（`src/server/llm/rateLimit.ts`）。上限は **1分に6回・1日に100回**（`src/lib/constants.ts` の `RATE_LIMIT_MINUTE`・`RATE_LIMIT_DAY`）。こえたら 429 と、混雑と同じ文（code は `busy`）を返す。こえた呼び出しは数えない。1時間つかっていない uid の記録は捨て、記録する uid は 10,000 件まで
  - 2回目（`/api/questions/detail`。#165）は、別の入れものに数える：**1分に12回・1日に200回**（`RATE_LIMIT_DETAIL_MINUTE`・`RATE_LIMIT_DETAIL_DAY`）。理由は 5.3.1
  - 数えない：ローカル版（`NEXT_PUBLIC_BACKEND=local`）と、AI を呼ばない見本の問い（`fallback` と `scene` つき）。デモ版（`/demo`）はそもそも API を呼ばない
  - リクエストの大きさ：`Content-Length` が 2MB（`MAX_REQUEST_BYTES`）をこえたら、JSON を読む前に 400。`Content-Length` がないリクエストは、Vercel の 4.5MB の上限と、画像の長さの検証（`request.ts`）で止める
  - 限界：回数はサーバーのメモリの Map で数える（サーバーは DB を持たない決まり）。Vercel の関数は何台かに分かれ、休むと記録が消えるので、台ごとに数えることになる。1台をたたきつづけることは止められるが、台数ぶんの上限までは通る
  - **人間の作業：Anthropic のコンソール（Settings の Limits）で、月の使用額の上限を決めておく**。上の歯止めをすりぬけても、費用がそこで止まる。発表の前に設定する
  - 【未決】ちゃんとした上限（Vercel KV・Firebase App Check など）は、新しいサービスが要るので、人間に確認してから決める（`AGENTS.md` 禁止事項3）
- グループの共有を広げるときは、モデレーション API（`docs/01-overview.md` 11章）が必要（いまは、メンバーの通報と、管理者が `/teacher/groups` から消す形。通報された投稿を自動で隠す・通報の乱用への対策は、広げるときに決める）
- ブラウザの安全のためのヘッダー：`next.config.ts` の `headers()` で、全部のパスに `X-Content-Type-Options: nosniff`・`Referrer-Policy: strict-origin-when-cross-origin`・`X-Frame-Options: DENY`・`Permissions-Policy: camera=(self), microphone=(), geolocation=()` を付ける（カメラは自分のサイトの中だけ。マイクと位置情報は使わない）
  - 【未決】`Content-Security-Policy`。Firebase（認証・Firestore）とフォントの読み込みをこわすおそれがあるので、いまは入れていない。入れるときは、本番と同じビルドでログイン・撮影・問いを作る流れを通して確かめる
- ホーム画面に追加（PWA）：`src/app/manifest.ts` の `theme_color` は `#4a5ae8`（`src/app/layout.tsx` の `viewport.themeColor` と同じ）、`background_color` は `#ffffff`。アイコンは `public/icon-192.png`・`public/icon-512.png`（Android）と `src/app/apple-icon.png`（180×180・iPhone）。どれも `src/app/icon.png` を縮小したもの
